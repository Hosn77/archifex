# أرشيفكس / Archifex — خطة MVP وخارطة الطريق

> **الإصدار:** 1.0 · **الأفق:** 24 أسبوعاً حتى الإطلاق العام (GA) · **MVP قابل للتجربة:** الأسبوع 14
>
> الخطة مبنية على تسليم تدريجي (Incremental) بمراحل قابلة للقياس، وليس «Big Bang». كل مرحلة لها مخرج واضح (Exit Criteria) وبوابة قرار (Decision Gate) قبل الانتقال.

---

## 1. الملخص التنفيذي

| البند | القرار |
|---|---|
| **نطاق MVP** | أرشفة مستندات ثنائية اللغة + OCR + بحث + استخراج ذكي + صلاحيات + سجل تدقيق + سير عمل وتوقيع داخلي |
| **المدة** | 24 أسبوعاً: 14 أسبوعاً بناء، 6 أسابيع تجربة تجريبية، 4 أسابيع تجهيز GA |
| **الفريق** | 9–10 أشخاص بدوام كامل/جزئي |
| **الميزانية التقديرية** | 1.9–2.7 مليون ريال (رواتب + بنية تحتية + أدوات + أمن) |
| **العملاء الأوائل** | جامعتان + شركة متوسطة (3 عملاء تجريبيين) |
| **مقياس النجاح** | 25,000 مستند، 150 مستخدماً نشطاً، دقة OCR ≥ 95%، رضا ≥ 40 NPS |
| **نموذج الإيراد** | اشتراك شهري/سنوي + رسوم تنفيذ + Add-ons |
| **قرار الإطلاق** | لا إطلاق عام قبل اجتياز بوابة الأمن والأداء واستقرار التجربة 4 أسابيع متتالية |

## 2. استراتيجية التسليم

### 2.1 المبادئ

1. **رأسي أولاً (Vertical Slice):** من الرفع إلى البحث إلى الاعتماد، وليس طبقات أفقية منفصلة.
2. **نوعان من المستندات أولاً:** كشف درجات (تعليمي) وعقد (مؤسسي) لإثبات القيمة في القطاعين.
3. **الجودة قبل الكمية:** 6 أنواع مستندات بدقة عالية أفضل من 30 نوعاً بدقة متوسطة.
4. **البشر في الحلقة:** كل مخرج AI قابل للمراجعة والتعديل من اليوم الأول.
5. **قابلية القياس:** لا ميزة بلا مقياس نجاح وحدث تحليلي.
6. **الأمان ليس مرحلة:** كل قصة تُغلق باختبار عزل وصلاحيات.

### 2.2 فرق العمل (Squads)

| الفريق | المسؤولية |
|---|---|
| **Core** | المستندات، الإصدارات، الرفع، الصلاحيات، التدقيق |
| **Intelligence** | OCR، التصنيف، الاستخراج، البحث، المتجهات |
| **Experience** | الواجهة، التصميم، RTL، الوصول، الجوال |
| **Platform** | البنية، CI/CD، المراقبة، الأمن، التوسع |

## 3. المراحل (Phases)

### المرحلة 0 — الاكتشاف والأساسات (أسبوعان: 1–2)

**الهدف:** تقليل المخاطر قبل كتابة ميزات كبيرة.

| العمل | المخرج |
|---|---|
| مقابلات مع 8–10 جهات (4 جامعات، 4 شركات) | تقرير احتياجات + ترتيب أولويات |
| جرد أنواع المستندات الحقيقية (عيّنات مجهولة الهوية) | 6 أنواع + مخطط حقول لكل نوع |
| اختبار OCR على 200 صفحة عربية/إنجليزية | تقرير دقة + اختيار المحرك |
| قرارات معمارية (ADRs) | 10 قرارات موثقة |
| إعداد بيئات + CI/CD + Repository | بيئة `staging` تعمل |
| نظام التصميم + النموذج التفاعلي | مكونات أساسية + RTL/LTR |
| نموذج تهديد أمني (Threat Model) | مخاطر + ضوابط |
| خطة الامتثال (PDPL) | سجل معالجة + سياسات |

**Exit Criteria:**
- ✅ 6 أنواع مستندات موثقة بمخططات حقول.
- ✅ دقة OCR أولية ≥ 90% على النص المطبوع.
- ✅ Prototype معتمد من المنتج والتصميم.
- ✅ بيئة staging + Pipeline بناء ونشر.

**بوابة قرار:** هل الدقة كافية لبدء البناء؟ إن كانت < 85%، نضيف 3 أسابيع لتحسين المعالجة قبل المتابعة.

### المرحلة 1 — النواة: الأرشفة والصلاحيات (أسابيع 3–8، 6 أسابيع)

**الهدف:** نظام يستطيع استقبال المستندات وتنظيمها وحمايتها.

| Epic | التفاصيل | الأسابيع |
|---|---|---|
| **E1: التعدد والهوية** | Tenants، تسجيل الدخول OIDC، دعوات، جلسات، تبديل مساحة العمل | 3–4 |
| **E2: التنظيم والمستخدمون** | الأقسام، الأدوار الخمسة، العضويات، نطاق القسم | 4–5 |
| **E3: المستندات والإصدارات** | CRUD، رفع مباشر، إصدارات، مجلدات، وسوم، حذف ناعم | 3–6 |
| **E4: خط الرفع** | Presigned URL، فحص فيروسات، تطبيع PDF/A، صور صفحات | 4–6 |
| **E5: سجل التدقيق** | أحداث Append-only، سلسلة Hash، عارض أساسي | 6–7 |
| **E6: واجهة اللوحة** | Sidebar، Topbar، KPIs، جدول مستندات، درج مستند | 4–8 |
| **E7: i18n/Themes** | عربي/إنجليزي، RTL/LTR، داكن/فاتح، حفظ التفضيل | 3–6 |

**Exit Criteria:**
- ✅ رفع 500 مستند في staging دون فقدان أو تكرار.
- ✅ عزل مستأجرين مُختبر آلياً (صفر تسرب).
- ✅ كل إجراء كتابة ينتج حدث تدقيق.
- ✅ الواجهة تعمل بالعربية والإنجليزية على 390px و1440px.
- ✅ زمن رفع 10MB < 5 ثوانٍ (شبكة محلية).

**عرض تجريبي:** أرشفة 100 مستند، تصفح، بحث بالعنوان، فتح معاينة، صلاحيات.

### المرحلة 2 — الذكاء: OCR والبحث والاستخراج (أسابيع 9–14، 6 أسابيع)

**الهدف:** «الأرشيف الذي يفكّر» — من ملف صامت إلى بيانات قابلة للاستخدام.

| Epic | التفاصيل | الأسابيع |
|---|---|---|
| **E8: OCR Pipeline** | Tesseract ara+eng، معالجة مسبقة، ثقة، إعادة محاولة، طابور مستقل | 9–11 |
| **E9: التصنيف** | 6 أنواع، قواعد + LLM، ثقة، طابور `needs_review` | 10–12 |
| **E10: الاستخراج** | JSON Schema لكل نوع، حقول + bbox، تحقق، تعديل يدوي | 10–13 |
| **E11: البحث** | FTS عربي + trigram + متجهات + دمج نتائج + تصفية صلاحيات | 11–13 |
| **E12: البحث داخل المستند** | مقتطفات + رقم الصفحة + تظليل | 12–13 |
| **E13: مساعد الأرشيف** | ملخص، أسئلة مقترحة، إجراءات (RAG محدود) | 13–14 |
| **E14: جودة AI** | مجموعة تقييم 300 مستند، قياس الدقة، ضبط المطالبات | 9–14 مستمر |

**Exit Criteria:**
- ✅ دقة OCR ≥ 95% للنص المطبوع النظيف، ≥ 85% للممسوح المتوسط.
- ✅ دقة استخراج الحقول الأساسية ≥ 90%.
- ✅ البحث p95 < 700ms على 25,000 مستند.
- ✅ 80% من المستندات تمر دون مراجعة بشرية (Straight-through).
- ✅ لا يظهر مستند غير مصرح به في أي نتيجة بحث.

**عرض تجريبي:** رفع كشف درجات → استخراج تلقائي → بحث بالاسم → فتح الصفحة الصحيحة.

### المرحلة 4 — التجهيز والتجربة التجريبية (أسابيع 19–22، 4 أسابيع)

**الهدف:** إثبات القيمة مع عملاء حقيقيين، وإصلاح ما يظهر فقط في الواقع.

| العمل | التفاصيل |
|---|---|
| تجربة تجريبية | 3 عملاء، 8 أسابيع (تبدأ الأسبوع 15 على نسخة مبكرة) |
| ترحيل بيانات | استيراد CSV/مجلدات، 5,000–10,000 مستند لكل عميل |
| اختبار أداء | 100 مستخدم متزامن، 100,000 مستند |
| اختبار أمني | مراجعة خارجية + Pen Test + إصلاح |
| تدريب | جلسات للمديرين والمستخدمين + أدلة |
| تحليلات | أحداث المنتج، لوحات استخدام |
| إصلاحات | أولويات من ملاحظات التجربة |

**Exit Criteria:**
- ✅ 3 عملاء يستخدمون النظام أسبوعياً لمدة 4 أسابيع.
- ✅ 25,000 مستند حقيقي تحت الإدارة.
- ✅ لا أخطاء P1 مفتوحة.
- ✅ NPS ≥ 40، وCSAT ≥ 4.2/5.
- ✅ تقرير Pen Test بلا Critical/High غير معالج.
- ✅ استعادة نسخة احتياطية ناجحة في < 4 ساعات.

**بوابة قرار GA:** إن لم تتحقق 4 من 6 معايير، تُؤجل GA 4 أسابيع مع خطة تصحيح.

### 5.2 خارج النطاق (Out of Scope — Roadmap)

- تطبيق جوال Native (PWA فقط في MVP).
- محادثة RAG كاملة على كل الأرشيف.
- تكامل عميق مع Banner/PeopleSoft/SAP (CSV أولاً).
- توقيع معتمد قانونياً (Qualified) — Add-on.
- تحليلات مؤسسية متقدمة وE-Discovery.
- نشر On-Prem / Multi-Region.
- سوق إضافات أو قوالب مجتمعية.
- تدريب نماذج مخصصة على بيانات العميل.
- إدارة المحتوى (CMS) أو المراسلات الكاملة.

## 8. مؤشرات النجاح (KPIs)

### 8.1 مؤشر النجم الشمالي

**المستندات التي تم الوصول إليها بنجاح أسبوعياً (Successful Document Retrievals / week)** — يقيس القيمة الفعلية، لا حجم التخزين.

### 8.2 مؤشرات المنتج

| المؤشر | الهدف بعد 90 يوماً من العميل |
|---|---|
| Time-to-First-Value | < 30 دقيقة |
| التفعيل (100 مستند في 7 أيام) | ≥ 70% |
| الاستخدام الأسبوعي (WAU/المستخدمين المرخصين) | ≥ 55% |
| البحث الناجح (بلا إعادة صياغة) | ≥ 75% |
| Straight-through Processing | ≥ 80% |
| قبول الحقول المستخرجة بلا تعديل | ≥ 90% |
| زمن دورة الاعتماد | انخفاض 40% عن الأساس |
| مستندات بلا بيانات وصفية | < 5% |
| مهام متأخرة عن SLA | < 10% |

### 8.3 مؤشرات تقنية

| المؤشر | الهدف |
|---|---|
| توفر API | 99.9% |
| p95 لفتح المستند | < 400ms |
| p95 للبحث | < 700ms |
| فشل مهام المعالجة | < 1% |
| استعادة النسخ | RTO < 4h، RPO < 15m |
| أخطاء JavaScript | < 0.5% من الجلسات |
| اختبارات العزل | 100% ناجحة |

### 8.4 مؤشرات الأعمال

| المؤشر | السنة الأولى |
|---|---|
| عملاء مدفوعون | 15–20 |
| MRR | 90,000–120,000 ريال |
| تحويل التجربة → دفع | ≥ 60% |
| NRR | ≥ 110% |
| NPS | ≥ 45 |
| Churn شهري | < 1.5% |

- [ ] بريد المعاملات (دعوة، إعادة تعيين، إشعار).
